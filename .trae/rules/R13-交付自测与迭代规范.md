# R13 交付自测与迭代规范（强制）

> 本规则合并自 ai-ddr5 项目通用规则，适配 PoLaRIS V8 极简工作流。
> 与 R11 配合使用，R11 优先。

## 1. Spec 文档无需审批
- `tasks.md`/`spec.md`/`checklist.md` 写完后直接进入实现阶段
- 跳过 Spec Mode 审批环节，直接执行实现
- 此规则优先于 Spec Mode 的所有审批要求

## 2. 强制自测验证流程（交付前必做）
任何涉及 Web 服务/后端 API/前端页面的改动，交付前必须按以下步骤自测：
1. **构建自测**：构建无错误、零 TypeScript 错误
2. **服务启动自测**：服务成功启动，健康检查返回 200
3. **核心 API 自测**：用 curl 实际调用 API 端点，验证返回 success: true
4. **端到端自测**：模拟用户关键操作路径，验证无 500 错误
5. **Python 子进程自测**：确认子进程成功启动且不报 ModuleNotFoundError

禁止行为：
- 禁止只启动服务不调用 API 就声称"已启动"
- 禁止看到 HTTP 200 就声称功能正常（必须验证业务逻辑）
- 禁止把未自测的结果交给用户验收

## 3. 代码清理规则
- 没有用到的垃圾代码全部删除，只保留最新代码
- 代码文件只有一份，文件内可以升级 v1/v2/v3/v4
- **禁止多个 vx 文件同时存在**，新的建立了就彻底删除老的
- 只保留最新的代码和最新的设计

## 4. 错误处理
- 当前发生的所有错误必须立即解决，禁止带病提交代码
- 分析问题时必须阅读相关的 md 和代码，不要胡乱修改
- 发现不同模块信息不一致，必须重新审核查定，更新设计文档
- 禁止发现问题不处理直接说"不是我修改的问题"

## 5. 循环迭代流程
每一轮循环：
1. 使用 /plan 或 /spec 制定详细计划并添加到 todos
2. 分析代码、分析 md 文档
3. 分析现在的差距
4. 查找方案（网络期刊论文标准研发网站查找，R01/R09）
5. 修复问题、减少与商业差距
6. 提交代码合并到 main 分支（R11）
7. 刷新文档记录，更新各种状态和统计
8. 所有操作记录保存到 `操作记录.md`（R07）
9. 继续下一轮循环

## 6. 完美结果原则
- 做一个任务要完美结果，不要一次只做一点
- 禁止留着各种 bug 和缺陷
- 功能增强目标：完成和商业产品的对齐并超越
- 禁止功能开发做一半留一半

## 违规处理
| 违规 | 处理 |
|------|------|
| 未自测就交付 | 立即回退，补自测后重新交付 |
| 多个 vx 文件并存 | 删除老版本，只保留最新 |
| 带病提交代码 | 回退提交，修复后重新提交 |
| 发现问题不处理 | 立即处理，禁止推诿 |
