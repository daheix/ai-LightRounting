## 3. 公式与理论依据

### 3.1 综合得分计算

PoLaRIS 综合得分采用加权平均：

$$
S = \sum_{i=1}^{N} w_i \cdot s_i
$$

**变量定义**：
- $S$：综合得分（0-10 分）
- $w_i$：第 $i$ 个维度权重（$\sum w_i = 1$）
- $s_i$：第 $i$ 个维度得分（0-10 分）
- $N$：维度数

**推导来源**：PoLaRIS 商业差距分析（`/workspace/docs/commercial_gap_analysis.md`）。

### 3.2 阶段 2 维度权重

阶段 2（追赶 KLayout + gdsfactory）的维度权重：

| DRC 引擎 | 0.15 | 6.5 | 8.0 | +0.225 |
| LVS 引擎 | 0.10 | 5.5 | 7.5 | +0.200 |
| PDK 生态 | 0.15 | 5.0 | 8.0 | +0.450 |

**推导来源**：阶段 1 验收得分 6.8（`/workspace/docs/commercial_gap_analysis.md`）+ R07-R11 各路标预期提升。

### 3.3 功能覆盖率

功能覆盖率：

$$
\eta_{\text{feature}} = \frac{N_{\text{covered}}}{N_{\text{total}}} \times 100\%
$$

**变量定义**：
- $N_{\text{covered}}$：已覆盖功能数
- $N_{\text{total}}$：总功能数（KLayout + gdsfactory 功能并集）

**阶段 2 目标**：$\eta_{\text{feature}} \geq 95\%$。

### 3.4 性能加速比

性能加速比：

$$
\text{Speedup} = \frac{T_{\text{baseline}}}{T_{\text{PoLaRIS}}}
$$

**变量定义**：
- $T_{\text{baseline}}$：基线工具（KLayout/gdsfactory）运行时间
- $T_{\text{PoLaRIS}}$：PoLaRIS 运行时间

**阶段 2 目标**：
- DRC：$\text{Speedup} \geq 5\times$（vs KLayout flat）
- LVS：$\text{Speedup} \geq 3\times$（vs KLayout）
- 布线：$\text{Speedup} \geq 3\times$（vs gdsfactory `route_astar`）

### 3.5 布线成功率

布线成功率：

$$
\eta_{\text{route}} = \frac{N_{\text{success}}}{N_{\text{total}}} \times 100\%
$$

**阶段 2 目标**：$\eta_{\text{route}} \geq 98\%$。

### 3.6 缓存命中率

PCell 缓存命中率：

$$
\eta_{\text{cache}} = \frac{N_{\text{hit}}}{N_{\text{hit}} + N_{\text{miss}}} \times 100\%
$$

**阶段 2 目标**：$\eta_{\text{cache}} \geq 90\%$。

## 4. 开源方案缺点分析（阶段 2 总结）

### 缺点 1：KLayout + gdsfactory 工具链割裂

- **问题描述**: KLayout（DRC/LVS/版图查看）与 gdsfactory（PDK/布线/PCell）是两个独立工具，需手动切换，数据通过 GDS 文件传递，无统一数据模型。
- **影响**: 设计流程割裂，元数据丢失（GDS 文件不保留 Python 对象元数据）。
- **来源 URL**: https://github.com/KLayout/klayout + https://github.com/gdsfactory/gdsfactory
- **根因分析**: 历史原因，KLayout 用 C++/Ruby，gdsfactory 用 Python，无统一 IR（Intermediate Representation）。
- **PoLaRIS 解决方案**: PoLaRIS 用统一 Python IR（`CircuitSpec` / `Device` / `Port`），DRC/LVS/布线/PCell 共享同一数据模型。

### 缺点 2：KLayout + gdsfactory 无 AI 集成

- **问题描述**: KLayout 与 gdsfactory 均无 LLM/AI 集成，DRC 规则生成、LVS 错误诊断、布线参数调优、PCell 代码生成均需人工。
- **影响**: 设计周期长，新手门槛高。
- **来源 URL**: https://github.com/KLayout/klayout + https://github.com/gdsfactory/gdsfactory
- **根因分析**: 两个工具均为传统 EDA 工具，设计时未考虑 AI 集成。
- **PoLaRIS 解决方案**: PoLaRIS 在 R07-R11 五个路标中均引入 AI 辅助（AI DRC 规则生成、AI LVS 诊断、AI 布线参数调优、AI PCell 生成）。

### 缺点 3：KLayout + gdsfactory 性能瓶颈

- **问题描述**: KLayout flat 模式 DRC 在大版图上 >10h（GF180 案例），gdsfactory `route_astar` 在大网格上 >10s/route。
- **影响**: 大规模 PIC 设计周期长。
- **来源 URL**: https://wiki.f-si.org/images/1/19/FSiC2023_KLayout_DRCLVS_best_practices.pdf
- **根因分析**: KLayout flat 模式不利用层次化结构；gdsfactory 用 `networkx` 纯 Python A*，无 JPS 剪枝/GPU 加速。
- **PoLaRIS 解决方案**: PoLaRIS 用层次化 BVH（OpenDRC 算法）+ JPS 剪枝 + GPU 加速。

### 缺点 4：gdsfactory 版本兼容性问题

- **问题描述**: gdsfactory 8.18.0 锁定 `pydantic<2.10`，与 Python 3.14 不兼容。
- **影响**: 新版 Python 用户无法使用 gdsfactory。
- **来源 URL**: https://gdsfactory.github.io/gdsfactory/changelog.html
- **根因分析**: gdsfactory 上游版本锁定策略保守。
- **PoLaRIS 解决方案**: PoLaRIS 自动检测版本兼容性，降级处理。

### 缺点 5：KLayout Ruby DSL 学习曲线

- **问题描述**: KLayout DRC/LVS/PCell 用 Ruby DSL，与 Python 生态脱节。
- **影响**: 高校教学与企业采用受阻。
- **来源 URL**: https://www.klayout.org/doc-qt5/manual/drc_runsets.html
- **根因分析**: KLayout 历史选型 Ruby（2007 年）。
- **PoLaRIS 解决方案**: PoLaRIS 全 Python API，无 Ruby 依赖。

- **风险**: 性能基准受硬件环境影响，需多次测量取中位数。
